              Specter
              
Transparent Task Manager replacement

            

            Desktop app
          

          
A transparent, fully customizable Task Manager replacement for Windows: Processes, Performance, Startup, and Services in one see-through window, with process controls stock Task Manager doesn't expose, like per-core CPU affinity, end-task-tree, and a floating always-on-top mini widget.

          
Live stats come from one persistent PowerShell worker streaming JSON over stdout instead of spawning a fresh process every tick, computing CPU% from Get-Process time deltas, the same math Task Manager itself uses, so it kept working even after a broken performance-counter provider on my own machine ruled out the more obvious approach.

              Wraith
              
Transparent Notepad + terminal workspace

            

            Desktop app
          

          
A transparent, tabbed Windows workspace that fuses Notepad, a Command Prompt, and a WSL Ubuntu terminal into one see-through window. Pick a tile from the launcher and it opens as its own tab, so notes and terminals sit side by side instead of in separate apps.

          
Actual cmd.exe and wsl.exe processes run through node-pty and render with xterm.js, notes autosave on a timer, and a global hotkey summons the window from anywhere, the same convention VS Code uses for its terminal.

                  Séance
                  
Multi-project status dashboard + CLI

                

                Desktop app
              

              
A transparent, summonable dashboard for keeping track of several projects at once: live git status, a per-project journal, an encrypted secrets vault, one-click sync between a WSL dev copy and its Windows counterpart, and a background test/build runner that notifies on pass or fail. A matching command-line tool reads and writes the exact same data, so status and notes stay current whether the window is open or not.

              
Because the CLI runs under WSL and the window itself runs as a native Windows process against the same on-disk data, project paths have to be translated between WSL's and Windows's own notations at the point of use, and every write goes through a real cross-process file lock with an atomic rename rather than a naive single-writer assumption, so two terminals touching the same project at once can't silently clobber each other.

                  Revenant
                  
Explorer replacement with instant whole-drive search

                

                Desktop app
              

              
A stock Windows Explorer replacement: whole-drive file search that returns instantly by reading the NTFS Master File Table directly instead of walking the filesystem, kept live via the USN Journal, plus real directory browsing, a 24h delete/edit recovery safety net, and tags.

              
Node's own fs module misclassifies a raw volume handle as a directory on the Node version Electron currently bundles, so search runs through a small native C++ addon that calls Win32's CreateFile/ReadFile directly instead, bypassing fs entirely, one of several corruption and data-loss edge cases I found and fixed in a dedicated bug-scan pass.

Technical note
Live updates trust the USN Journal the instant an event is seen rather than re-reading the file record, because a raw volume read of a just-deleted file still showed it as in-use 4+ seconds later, while the journal entry was already there.

      WORKING AGREEMENTTerms
      
    
    
    
    
      
    These are the terms I work under on any paid engagement. They exist so both sides know what to expect going in, and so anything that goes wrong gets handled fairly rather than argued about after the fact. Starting a paid project means both sides have agreed to them.
    

      
    
        
    1. Work environment
    
        
    I work with people who communicate respectfully. Specifically:
    
        
      
          
    1. No yelling, no talking down to me, and no unreasonable pressure or last-minute demands.
      2. 
          
    2. If a conversation turns toxic, I may end the project immediately and walk away.
      3. 
          
    3. Payment following an early end under this clause is settled under clause 5, based on work actually completed, not a blanket refund or a full forfeit.
      4. 
        
    
        
    Example: a client starts yelling on a call or sending demanding, disrespectful messages. I end the engagement and settle payment for whatever was already built.
    
      
    

      
    
        
    2. Scope
    
        
    Before I write a line of code, we agree in writing on what's actually being built. Specifically:
    
        
      
          
    1. Scope changes are normal and expected, but they get discussed and priced before I build them.
      2. 
          
    2. Work outside the agreed scope is not assumed to be included for free.
      3. 
          
    3. Scope changes can go the other way too. In rare cases, if something originally quoted turns out to be unnecessary or gets cut before I build it, the price can be adjusted down from the original quote, though this is the exception rather than the rule.
      4. 
        
    
        
    Example: you ask for a login system partway through a project that didn't originally include one. That's a scope change, it gets a price and timeline before I start it, not silently folded into the original quote. If instead you decide a feature I quoted for isn't needed after all and I haven't built it yet, the price can come down to reflect that.
    
      
    

      
    
        
    3. Deadlines
    
        
    Timelines are set to be realistic, not optimistic. Specifically:
    
        
      
          
    1. If something is going to be late, I'll say so as soon as I know, not on the deadline itself.
      2. 
          
    2. In return, I expect the same honesty about your side, assets, feedback, or access I need from you to keep the project moving.
      3. 
        
    
        
    Example: I said Friday and it's actually going to be Monday. You hear that from me by Wednesday, not Friday afternoon.
    
      
    

      
    
        
    4. Communication
    
        
    How and how fast I respond depends on the channel. Specifically:
    
        
      
          
    1. Discord is my preferred channel. I check it constantly through the day, so it's the fastest way to reach me.
      2. 
          
    2. Email works too, but responses may take noticeably longer since I check it far less often.
      3. 
          
    3. Regardless of channel, you should expect a reply within about a day under normal circumstances.
      4. 
        
    
        
    Example: a Discord message sent on a Tuesday usually gets a same-day reply. The same message sent by email might not get a response until the next day.
    
      
    

      
    
        
    5. Payment
    
        
    Money is agreed on before work starts, not figured out after. Specifically:
    
        
      
          
    1. Price and payment structure are agreed upfront, in writing, before work starts.
      2. 
          
    2. I accept payment in Robux, Euro/cash, or, in rare cases, a revenue share or ownership stake, sent via PayPal, Paysafecard, or Robux.
      3. 
          
    3. For larger projects, I may ask for a portion upfront; the remainder is due on delivery, not whenever it's convenient.
      4. 
          
    4. If a project ends early because these terms are violated, payment is worked out based on how much was actually completed at that point, not a fixed all-or-nothing refund.
      5. 
        
    
        
    Example: a $600 project that's roughly half delivered when it ends early under these terms settles around $300, not $0 and not the full $600.
    
      
    

      
    
        
    6. Ownership
    
        
    Who owns the code and assets, and when that changes. Specifically:
    
        
      
          
    1. Everything I build (code, designs, and other assets) stays my intellectual property until it's paid for in full.
      2. 
          
    2. Ownership transfers to you only once payment is complete and only if that transfer was agreed in writing beforehand. No written agreement to transfer ownership means you get a license to use what was delivered, not the underlying rights to resell or relicense it.
      3. 
          
    3. Work I reuse across projects (personal tools, libraries, boilerplate I wrote before or outside your project) stays mine regardless of payment status.
      4. 
        
    
        
    Example: you pay in full for a Discord bot with no other agreement in writing. You can run and use that bot. You can't resell the source code as your own product unless that was separately agreed.
    
      
    

      
    
        
    7. Enforcement
    
        
    These terms exist to protect both sides, not to force an outcome. Specifically:
    
        
      
          
    1. If something in clauses 1 through 6 is technically triggered, I can choose to invoke it right away, or choose to keep the project going if I think it's still workable.
      2. 
          
    2. Letting something go once doesn't waive my right to invoke that same term later if it happens again.
      3. 
        
    
        
    Example: a deadline slips once and I decide it's not worth ending things over, so I just keep going. If it becomes a pattern, I can still invoke clause 3 later even though I let the first one slide.
